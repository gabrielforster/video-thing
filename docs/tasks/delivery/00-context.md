> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Take the whole application from "runs on my laptop against LocalStack" to "runs on AWS behind one CloudFront distribution", deployed by an OIDC-authenticated GitHub Actions pipeline, with migrations as an explicit gated step.

**Architecture:** Three container images (`api`, `worker`, `migrations`) built from one repository and pushed to ECR tagged with the commit SHA. Terraform owns everything in AWS; the pipeline's only imperative actions are `docker push`, `aws s3 sync` of the Vite build, one `ecs run-task` for migrations, and waiting for the ECS services to stabilise. The database password is generated by Terraform, stored in Secrets Manager, and injected into containers by the ECS agent — it never appears in a workflow file, an image, or the repository.

**One distribution, three origins.** Everything a browser touches arrives on a single `*.cloudfront.net` name with no domain and no ACM certificate: the default behaviour serves the Vite build from a private S3 bucket via Origin Access Control, `/processed/*` serves HLS from the private processed-assets bucket with §15's three TTLs, and the five paths `openapi.yaml` defines go to the ALB uncached. That makes the browser **same-origin with the API**, which is what removes the mixed-content problem a separate HTTP ALB hostname would have caused. `PUBLIC_ASSET_BASE_URL` becomes the distribution domain — still contract 4, one variable, no code branching.

**Tech Stack:** Docker (multi-stage, alpine runtime), statically-linked Go binaries, `mwader/static-ffmpeg`, golang-migrate, Terraform 1.10+ with the AWS provider ~> 5.0, ECS Fargate, ECR, SQS + DLQ, CloudFront (two OAC S3 origins + an ALB origin, three cache policies, a CORS response-headers policy), S3 gateway VPC endpoint, Secrets Manager, CloudWatch, GitHub Actions with OIDC.

**Depends on:** [api-list-delete-plan.md](api-list-delete-plan.md) (`GET /videos`, `DELETE /videos/{id}`) and [worker-rendition-ladder-plan.md](worker-rendition-ladder-plan.md) (the rendition ladder) for the *features* that will eventually run in these containers. Nothing in this plan blocks on them: it ships images, infrastructure, and a pipeline for the code that exists today, and every task is independently verifiable against the current `master`. Task 4 touches one constant in `apps/worker/consumer.go`, which the rendition-ladder plan also edits — see the note in that task.

## Global Constraints

- Go 1.25.5, single root module `github.com/gabrielforster/video-thing`. No `go.work`, no per-app module.
- Every task ends gofmt-clean (`gofmt -l .` prints nothing), `go vet ./...` clean, `go test ./...` green.
- Web: pnpm only. `pnpm test` and `pnpm lint` green at every task boundary.
- Response shapes match `openapi.yaml` exactly, including the `{error:{code,message}}` envelope. **This plan changes no handler and no response shape.**
- Services never auto-migrate on boot. Schema changes are golang-migrate files run from a Makefile target or an explicit pipeline step (`video-thing-spec.md` §18, `database-schema.md` "CI/CD integration").
- Terraform: `terraform validate` and `terraform fmt -check` clean in every environment directory. `terraform fmt -check -recursive` clean under `infrastructure/terraform`.
- Secrets never land in the repo, in Terraform state committed to git, or in a Docker image. Zero GitHub **secrets** are required by this plan — only repository/environment **variables** (`AWS_ROLE_ARN`, `AWS_REGION`), neither of which is confidential.
- Tests before implementation, one commit per task minimum. Conventional commit prefixes (`feat:`, `fix:`, `docs:`, `chore:`, `refactor:`, `test:`). **Never add a `Co-Authored-By` trailer.**
- Comment discipline: a comment only where its absence causes a real bug or hides a deliberate decision (why an env var is *absent*, why a policy lives in the module it lives in). No comments in `_test.go` files.
- Image tags are the full commit SHA. `latest` is never deployed. ECR repositories are `IMMUTABLE`, so the push step is guarded by a `describe-images` check to keep re-runs idempotent.
- Every container runs as uid/gid `65532`, never root.
- Contract 4 is load-bearing: the asset URL shape stays `${PUBLIC_ASSET_BASE_URL}/processed/{id}/master.m3u8`. Moving to CloudFront is a change of that one environment variable and nothing else. No code in this plan branches on environment.
- **Sizing is the floor, not a capacity plan.** This is a demo. Every CPU, memory, instance-class, count, and retention value is the smallest that still works, with one named exception (the worker — see Task 3) and two safety values §6 of the master spec requires in production (`multi_az`, `skip_final_snapshot`). Any task that wants to raise a number states the arithmetic.
- The web app is a static bundle, not a container. `apps/web` is built with `pnpm build` and synced to S3; there is no `web` ECR repository and no Fargate service for it.

## What costs money while idle

Sizing is the floor everywhere (see Global Constraints), but three resources bill by the hour regardless: a NAT Gateway, an RDS instance, and an ALB. Approximate `us-east-1` on-demand figures, per month, at the published rates used in the arithmetic below:

| Resource | dev / staging | production | Arithmetic |
|---|---|---|---|
| NAT Gateway ×1 | $32.85 | $32.85 | 730 h × $0.045/h; the attached EIP is free while in use |
| RDS `db.t4g.micro`, 20 GB gp3 | $13.98 | $27.96 | 730 h × $0.016/h + 20 GB × $0.115; production doubles both for Multi-AZ |
| Application Load Balancer | $16.63 | $16.63 | 730 h × $0.0225/h + ~$0.20 idle LCU |
| Fargate API, 1 × 0.25 vCPU / 0.5 GB | $9.01 | $9.01 | 730 h × (0.25 × $0.04048 + 0.5 × $0.004445) |
| Fargate worker, 1 vCPU / 2 GB | $0.00 | $0.00 | `worker_min_count = 0`: scale-to-zero, §14. Billed only while transcoding |
| Secrets Manager, 2 secrets | $0.80 | $0.80 | 2 × $0.40 |
| CloudWatch, 5 alarms + 1 dashboard | $0.50 | $0.50 | 5 × $0.10; the first 3 dashboards are free |
| ECR storage, ~1 GB | $0.10 | $0.10 | $0.10/GB |
| S3 gateway VPC endpoint | $0.00 | $0.00 | gateway endpoints have no hourly charge |
| CloudFront, S3, SQS | $0.00 | $0.00 | usage-only, no idle floor |
| **Idle total** | **≈ $74/mo** | **≈ $88/mo** | before a single request |

All three environments applied at once is **≈ $236/month idle**. Apply `dev` only unless there is a reason not to.

**NAT Gateway versus VPC interface endpoints, with the numbers.** Tasks in private subnets need to reach ECR (image pull), Secrets Manager (`DATABASE_URL`), CloudWatch Logs, SQS, and S3. Replacing the NAT Gateway with interface endpoints means five of them — `ecr.api`, `ecr.dkr`, `logs`, `secretsmanager`, `sqs` — at $0.01/h each per AZ: **$36.50/month in one AZ, $73.00 in two.** One NAT Gateway is $32.85 and covers every destination with nothing to maintain. So: **one NAT Gateway, in every environment, including production.** What that costs is availability — the NAT lives in one AZ, so losing that AZ costs egress for private subnets in both, and the worker stops being able to read S3 or poll SQS until it recovers. The API keeps serving reads, because RDS is inside the VPC.

**The one endpoint that is free, and worth it anyway.** An S3 *gateway* endpoint has no hourly charge and routes S3 traffic off the NAT entirely. Video bytes are the dominant flow — the worker downloads each source and uploads every segment — so at $0.045/GB of NAT data processing, a 100 MB source producing 300 MB of renditions costs about $0.018 per video through the NAT and $0 through the endpoint. ECR image layers are also served from S3, so image pulls stop crossing the NAT too. Task 3 adds it. Nothing breaks: the endpoint only adds a more specific route for the S3 prefix list.

`terraform destroy` in `dev` and `staging` tears everything down. In `production` the RDS instance has `deletion_protection = true` and `skip_final_snapshot = false`, so `destroy` deliberately fails until a human disables protection. Do not run `terraform apply` casually, and never against `production` without reading the plan output.

## Deviations from the specs, recorded

1. **State locking.** `backend.tf` uses S3 native locking (`use_lockfile = true`, Terraform 1.10+) instead of the DynamoDB lock table in ADR-0005 and `github-oidc-role.md` §3.1. One less resource to provision and pay for; the `TerraformLock` DynamoDB grant in that document is now dead and the `core` policy omits it.
2. **Trust policy claim form.** `github-oidc-role.md` §2's example scopes `sub` to `ref:refs/heads/main`; this plan uses the `environment:` form the same section recommends for per-environment deploys. It also avoids the fact that this repository's default branch is `master`, not `main`.
3. **CI role policies are three managed policies, not one.** The document presents §3's statements as a single permission policy; an IAM role's aggregate *inline* policy budget is 10,240 characters and a managed policy caps at 6,144, so they are split into `core`/`data`/`compute`.
4. **The `web` ECR repository is dropped.** `modules/ecr`'s default `repository_names` includes `web`, but the web app is a static Vite bundle with no container. The environments pass `["api", "worker", "migrations"]` explicitly.
5. **`apps/worker/consumer.go`'s visibility timeout changes** from 120 s to 900 s (Task 4). This is application code in an infrastructure plan, justified because the DLQ's `maxReceiveCount` is meaningless while `ApproximateReceiveCount` tracks wall-clock time instead of failures. [worker-rendition-ladder-plan.md](worker-rendition-ladder-plan.md) also edits this file.
6. **`production` uses one NAT Gateway and two AZs, not per-AZ NAT and three.** §6 of the master spec names only `multi_az` and `skip_final_snapshot` as the production deltas, and both are honoured. Per-AZ NAT was this plan's own earlier choice, reversed on the owner's "smallest sizes everywhere" instruction with the arithmetic in "What costs money while idle". Recorded as an accepted gap rather than hidden.
7. **The SPA fallback maps 403 only, not 403 *and* 404.** Mapping 404 would rewrite `openapi.yaml`'s own `404` for an unknown video into a `200` carrying `index.html`, and `apps/web/src/api.ts`'s `json()` helper would try to parse HTML. Task 5 step 6 explains what makes 403-only correct and what would break it.
8. **`modules/cloudfront` grew past "the CDN for processed assets".** It is now the single front door — two OAC S3 origins plus the ALB — because a second distribution would mean a second hostname, and a second hostname is exactly the mixed-content and cross-origin problem this design exists to avoid.

## Decisions the owner settled, and where they landed

The four questions this plan originally could not answer were answered by the repo owner. All
four are now implemented rather than deferred, and none of them is a spec that still needs
writing.

1. **`apps/web` is served from S3 behind the same CloudFront distribution.** Task 5. One
   distribution, default certificate, three origins; the browser is same-origin with the API,
   which is what removes the mixed-content problem; `VITE_API_URL` is built as the empty string
   and `apps/web/src/api.ts` needs no change (verified against the built bundle, Task 5 step 2).
2. **Alarm notifications stay unwired.** No SNS topic and no subscription are created. Recorded
   as the first entry in "Accepted gaps" below, and surfaced in `README.md` by Task 9 step 4.
3. **Every size is the floor.** API at the Fargate minimum (256/512, one task), worker at
   1024/2048 because the four-rendition ladder needs it, `db.t4g.micro` with 20 GB, one NAT
   Gateway everywhere, 7-day log retention, `worker_max_count = 2`. Arithmetic in "What costs
   money while idle"; the two non-minimal values in `production` (`multi_az`,
   `skip_final_snapshot`) are there because §6 of the master spec names them.
4. **These plans are the only implementation document.** Nothing in this plan defers to a
   "delivery spec", an "infrastructure spec", or any other unwritten document. Task 9 step 5
   rewrites the two `vertical-slice-spec.md` §3 rows that pointed at them so they cite this
   plan's tasks instead. Everything this plan needed from a spec came from
   `video-thing-spec.md`, `openapi.yaml`, `ffmpeg-profiles.md`, `database-schema.md`,
   `sequence-diagrams.md`, or `github-oidc-role.md`, cited by section at the point of use.

## Accepted gaps

Deliberate and known. Task 9 step 4 puts this same list in `README.md` so it is discoverable
without reading a plan. Do not close one of these inside an unrelated task.

- **No alarm notifications.** Five alarms exist — queue depth, DLQ not empty, ALB 5xx, API CPU,
  worker CPU — and all five have an empty `alarm_actions` because `sns_alarm_topic_arn` is
  empty in every environment. They change state silently. Fixing it is additive: a topic, a
  subscription, and one variable; the `monitoring` module already threads the value through.
- **CloudFront reaches the ALB over plain HTTP.** The viewer hop is HTTPS, the origin hop is
  not. Needs a domain, an ACM certificate and an HTTPS listener on the ALB, and
  `origin_protocol_policy = "https-only"`. The ALB's security group admits only CloudFront's
  managed prefix list, which is network scoping — not encryption, and not origin
  authentication, since that prefix list covers every CloudFront distribution in every account.
- **The SPA fallback depends on S3 answering 403, not 404, for a missing key.** True because
  the bucket policy grants `s3:GetObject` without `s3:ListBucket`, and safe because
  `openapi.yaml` defines no 403. Granting `ListBucket`, or adding a 403 to the API when
  authentication lands (§17), breaks it — the fix is a CloudFront Function on the default
  behaviour, which is per-behaviour where `custom_error_response` is distribution-wide.
- **`production` is partially available by design.** Multi-AZ database, single NAT Gateway,
  single API task. `api_desired_count = 2` plus `single_nat_gateway = false` is the fix, at
  about +$42/month.
- **No blue/green or canary deploys.** A rolling ECS update with the deployment circuit
  breaker catches a release that fails to start, not one that starts cleanly and misbehaves.
- **`db.t4g.small` sizing was never needed.** No spec states a write rate and the schema has
  one table, so every environment runs `db.t4g.micro`. If that ever stops being true, the
  evidence will be the RDS CPU metric on the dashboard, not a guess.
