````markdown
## Deploy it to AWS

> Applying this provisions a NAT Gateway, an RDS instance, and an ALB, which bill by the
> hour whether or not anyone uses them — roughly **$74/month idle for `dev`** and
> **$88/month idle for `production`** in `us-east-1`, before a single request. Everything is
> already sized to the floor; those three resources have no smaller form.
> `terraform destroy` in `dev` removes
> everything; `production` has `deletion_protection = true` on purpose, so a destroy there
> fails until a human turns it off. See
> [docs/plans/delivery-plan.md](docs/plans/delivery-plan.md) for the per-resource breakdown.

One-time, as an account administrator:

```bash
GITHUB_REPOSITORY=<org>/<repo> AWS_REGION=us-east-1 ./scripts/bootstrap-aws.sh
```

That creates the Terraform state bucket (`video-thing-terraform-state`, versioned and
encrypted), the GitHub OIDC provider, and the role CI assumes, with the three permission
policies from
[docs/specifications/github-oidc-role.md](docs/specifications/github-oidc-role.md). It
prints the two values to set as GitHub repository **variables** — `AWS_ROLE_ARN` and
`AWS_REGION`. Then create GitHub Environments named `dev`, `staging`, and `production`; the
role's trust policy keys on the environment name, and `production` should have required
reviewers.

**No GitHub secret is required.** The database password is generated by Terraform, stored in
Secrets Manager, and injected into containers by the ECS agent — it never enters this
repository, a workflow log, or an image layer.

Then deploy from the Actions tab: **Deploy → Run workflow → environment**. The workflow
assumes the role via OIDC, ensures the ECR repositories exist, builds and pushes
`api`/`worker`/`migrations` tagged with the commit SHA, registers the migrations task
definition, runs migrations as a one-off Fargate task and fails the deploy on a non-zero exit
code, applies the rest of the stack, waits for both ECS services to reach steady state, then
builds the web bundle, syncs it to S3, and invalidates the four CloudFront paths that can be
stale. The last step prints one URL, which is the whole application.

Migrations never run on boot. They run as their own pipeline step, ordered strictly before
the new API/worker version rolls out, per
[video-thing-spec.md §18](docs/specifications/video-thing-spec.md#18-cicd) and
[database-schema.md](docs/specifications/database-schema.md#migration-strategy). To run them
by hand against an already-applied environment:

```bash
make migrate-aws ENV=dev
```

### One hostname, three origins

There is no domain and no ACM certificate. Everything arrives on the distribution's default
`*.cloudfront.net` name:

| Path | Origin |
|---|---|
| `/` and anything unmatched | the private web bucket, via Origin Access Control |
| `/videos`, `/videos/*`, `/healthz`, `/readyz` | the ALB, uncached — exactly the paths in [openapi.yaml](docs/specifications/openapi.yaml) |
| `/processed/*` | the private processed-assets bucket, with the [§15](docs/specifications/video-thing-spec.md#15-cdn-strategy) TTLs |

That makes the browser same-origin with the API, which is why the web app needs no API URL
at all: it is built with `VITE_API_URL` set to the empty string, so `apps/web/src/api.ts`
issues root-relative requests (`fetch('/videos')`) that the distribution routes to the ALB.
It is also what avoids mixed content — a page served over HTTPS cannot call an HTTP endpoint,
and the ALB has no HTTPS listener because that would need a domain.

Deep links like `/videos/{id}` work because the distribution maps a `403` to `/index.html`
with a `200`: S3 with Origin Access Control returns `403` for a missing key, and the API
returns no `403` anywhere in its contract. A `404` is deliberately *not* mapped, so the API's
own `404` for an unknown video still reaches the client intact.

### Container images

```bash
make images         # api, worker, migrations, tagged :local
make image-smoke    # builds them and asserts uid 65532, static linkage, ffmpeg version, /healthz
```

All three run as uid 65532 on `alpine:3.24.1`; the worker carries `ffmpeg`/`ffprobe` pinned
to `mwader/static-ffmpeg:7.1.1`. Every `FROM` names an exact patch version — bumps are a
deliberate commit that re-runs `make image-smoke` and `make e2e`.
````

````markdown
## Accepted gaps

Deliberate, known, and not to be "fixed" by a passing change without a decision.

**No alarm notifications.** `sns_alarm_topic_arn` is empty in `dev`, `staging`, and
`production`, so the `monitoring` module creates every alarm with an empty `alarm_actions`
list. Five alarms exist and all five currently notify nobody — they change colour in the
CloudWatch console and nothing else happens:

| Alarm | Fires when |
|---|---|
| `video-thing-<env>-sqs-queue-depth-high` | more than 100 visible messages for 15 minutes — the worker fleet is not keeping up |
| `video-thing-<env>-dlq-not-empty` | any message reaches the dead-letter queue — a job failed *and* recording the failure failed |
| `video-thing-<env>-alb-5xx-high` | more than 10 target 5xx responses per minute for 3 minutes |
| `video-thing-<env>-ecs-api-cpu-high` | API CPU above 85% for 15 minutes |
| `video-thing-<env>-ecs-worker-cpu-high` | worker CPU above 85% for 15 minutes |

Wiring it up is small and entirely additive: create an SNS topic, subscribe an email address
or a chat webhook, confirm the subscription, and set `sns_alarm_topic_arn` in the environment's
`variables.tf`. The `monitoring` module already threads that value into `alarm_actions` and
`ok_actions` on every alarm, and the CI role already has `sns:GetTopicAttributes`. It is left
undone on purpose, pending a decision about where alerts should land.

**CloudFront reaches the ALB over plain HTTP.** Viewers get HTTPS; the CloudFront-to-origin
hop does not, so API bodies cross AWS's network unencrypted. Closing it needs a domain name,
an ACM certificate and an HTTPS listener on the ALB, and `origin_protocol_policy = "https-only"`
on that origin. The ALB's security group already admits only CloudFront's managed prefix list,
so its hostname does not serve the public internet — but that is network scoping, not
encryption, and it is not origin authentication either, since that prefix list covers every
CloudFront distribution in every account.

**`production` is partially available, by design.** Multi-AZ RDS behind a single NAT Gateway
and a single API task: the database survives losing an availability zone, egress and the API
do not. Correct for a demo whose `production` exists to prove the deployment path; wrong for
anything with users. `api_desired_count = 2` and `single_nat_gateway = false` is the two-line
fix, at roughly +$42/month.

**No blue/green or canary.** Deploys are a rolling ECS update guarded by the deployment
circuit breaker, which rolls back on repeated task failure but cannot detect a release that
starts cleanly and behaves wrongly.
````
